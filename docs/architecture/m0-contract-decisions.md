# M0 contract decisions

- Status: implementation baseline frozen
- Reviewed: 2026-09-01
- Public broker protocol: 1
- Private Claude worker protocol: 1

M0 turns the architecture specification into executable boundaries without
starting the Neovim UI. Default verification is deterministic and offline;
provider-authenticated probes remain explicit operations.

## Frozen runtime baseline

| Component | Version | Role |
| --- | ---: | --- |
| Rust | 1.98.0 | broker and native Codex adapter |
| Python | 3.13.15 | isolated Claude worker runtime |
| uv | 0.12.7 | Python environment and dependency lock |
| Codex CLI | 0.152.0 | reviewed stable-v1 schema lower bound |
| Claude Code | 2.1.251 | tested SDK-bundled runtime baseline |
| Claude Agent SDK | 0.2.148 | tested worker-profile baseline |

Mise pins the toolchain. `python/uv.lock` pins the reproducible Python test
environment. The curated Codex bundle includes generated schema checksums, and
its update script refuses a different CLI release because changing the review
baseline is separate from running a newer compatible stable runtime.

## Framing decision

Agent Manager's public and private protocols use ordinary JSON-RPC 2.0 and
require the `jsonrpc` member. Codex App Server 0.152.0 uses newline-delimited
JSON but omits that member on the wire. The native adapter owns this difference;
it must not leak into the Neovim client or Claude worker.

Frames are bounded before full-line allocation. Duplicate object keys,
non-finite numbers, malformed callback IDs, and oversized frames are rejected.
JSON-RPC error responses may use `id: null` when a valid request ID could not be
recovered; ordinary requests may not.

The official [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server)
confirms the headerless wire format, initialization handshake, stable versus
experimental capability gate, generated per-version schemas, thread lifecycle,
turn steering, streaming events, and server-initiated approvals. M0 opts out of
the experimental API and vendors schemas generated by the installed CLI.

The 0.152.0 baseline adds a project sort-key enum, an optional per-turn timeout,
authentication-recovery notifications, and an OpenAI-form MCP elicitation
variant. The adapter does not opt into form elicitation, preserves the recovery
records as provider notices, and continues to deny unsupported server requests
rather than guessing a safe response.

Server-initiated Codex requests retain their opaque App Server request ID and
an explicit `response_required` state. The adapter exposes a dedicated response
operation; the diagnostic trace always denies. A callback that arrives while a
synchronous client request is still awaiting its response is denied
automatically so it cannot deadlock or accidentally approve an action.

## Claude session and callback decisions

The current [Python SDK reference](https://code.claude.com/docs/en/agent-sdk/python)
establishes `ClaudeSDKClient` as the persistent interactive client and exposes
`query`, `receive_response`, `interrupt`, specific `resume`, and
`fork_session`. Synchronous discovery and history calls run through bounded
executor work so they cannot block the protocol reader.

The current [approval and user-input guide](https://code.claude.com/docs/en/agent-sdk/user-input)
clarifies an important point that the original prose left ambiguous: normal
tool approvals and `AskUserQuestion` both enter through `can_use_tool`. The
worker distinguishes the tool name and exposes two typed broker callbacks,
`approval/request` and `question/request`. A disconnect, timeout, malformed
response, or shutdown returns denial; it never synthesizes approval.

SDK 0.2.148 is the tested M0 package baseline recorded by
[PyPI release metadata](https://pypi.org/project/claude-agent-sdk/). It supports
Python 3.13 and includes the session metadata/history and callback types used by
the worker. That release's
[bundled CLI metadata](https://github.com/anthropics/claude-agent-sdk-python/blob/v0.2.148/src/claude_agent_sdk/_cli_version.py)
pins Claude Code 2.1.251, so the worker uses and reports the bundled runtime
instead of whichever `claude` executable happens to appear on `PATH`.

For M0, `setting_sources=[]` and strict MCP configuration prevent a target
repository from injecting executable Claude configuration into the private
worker. A later provider-settings design may expose reviewed sources explicitly
without changing the process ownership boundary.

## Contract surface

The public schema freezes:

- agent summaries and precise lifecycle states;
- provider capability vocabulary;
- start, attach, history, prompt, steer, interrupt, resume, fork, archive,
  approval, question, context, diff, replay, and embedded shutdown requests;
- the monotonic event envelope and unknown-event preservation rule; and
- JSON-RPC response and broker-state notification framing.

The private schema freezes:

- nonce-bound worker initialization and diagnostics;
- session list, history, start, specific resume, fork, and close;
- prompt, steer, and interrupt;
- lossless worker event sequencing; and
- worker-initiated approval/question rendezvous.

## Verification evidence

Rust integration tests drive deterministic fake Codex and Claude worker
processes over real pipes. They prove initialization, discovery, session and
turn startup, streamed notifications, approval requests, fail-closed responses,
and shutdown without provider credentials. Rust framing tests prove bounded
allocation at exact limits. Python tests exercise bounded frame parsing,
explicit SDK encoding, discovery, history, specific resume and fork, concurrent
event flow, structured questions, callback responses, callback timeout denial,
and cleanup. Shared JSON fixtures and known-invalid cases are schema-validated;
public fixtures are also deserialized by Rust.

Live probes are separate:

- `codex-probe` initializes App Server and lists one history page without
  starting a model turn.
- `codex-trace` requires `--allow-live-provider`, starts a model turn, prints
  event names only, and denies command/file approvals by default.

No live provider probe is part of `mise run verify`.

## Upgrade rule

The broker's public protocol is not tied to one provider patch release. Codex
App Server 0.152.0 and newer runtimes enter the `codex-app-server-stable-v1`
profile only after the initialization handshake succeeds with experimental APIs
disabled. The Claude worker similarly advertises `claude-agent-sdk-v1`, actual
SDK and bundled-runtime versions, and structural compatibility. Agent summaries
and the durable registry record those actual identities.

Moving an installed executable within an existing compatibility profile does
not require a broker release. Running processes are not hot-upgraded; a later
resume uses the currently configured compatible runtime. Changing the schema
lower bound, enabling an experimental API, or changing a compatibility profile
is a reviewed contract change. Such a change must:

1. update the tested runtime/package baseline or compatibility profile;
2. regenerate or relock the provider artifacts;
3. review schema and SDK type diffs;
4. update adapters and golden fixtures;
5. pass fake-runtime verification; and
6. run the explicit credential-gated probes before the new baseline is
   declared supported.
